# Hosted 서울 단기예보 수집 복구

## 원인과 수집 소유권

2026-10-13 조사에서 R2의 마지막 `kma_vilage_fcst` 수집 날짜는 2026-09-18이었다.
로컬 Docker API는 연결되지 않았고 호스트 보호 기록은 `stopped`, `latched=true`,
`automatic_restart=false`, `docker_vm_memory_pressure`였다. 보호 정지 뒤 Airflow
수집이 재개되지 않아 최근 날짜의 raw와 완료 manifest가 없었다. 날짜 파티션은
실제 수집일이며 마지막 예보 발표 시각을 증명하는 것은 아니다.

동일 키로 최신/당일 새벽 기상청 응답을 제한 조회해 HTTP 200 및 날짜·격자 계약을
확인했다. 인증키 실패와 리포트 경로 오류가 주원인은 아니다. 실제 API 요청량과
계정 전체 할당량은 이 두 번의 조회로 증명되지 않는다.

복구 후 `Weather Raw Collection` GitHub workflow가 단기예보 raw 수집을 소유한다.
Mac의 보호 잠금, Airflow pause, Docker 중지 상태는 유지한다. 나중에 로컬 수집을
재개하려면 hosted를 먼저 비활성화하고 실행 중 작업이 끝난 것을 확인해야 한다.
서로 다른 실행기가 Airflow Pool이나 같은 API 할당량을 자동 공유한다고 가정하지 않는다.

## 수집 → 완료 근거 → 일일 품질

기존 `KmaLanding`, `KmaHttpAdapter`, `R2RawObjectStore`와 응답 계약을 재사용한다.
Airflow·Trino·Iceberg·D1·실황 데이터 가동은 이 복구 범위에 포함하지 않는다.
수집된 예보가 Silver/Gold나 공개 제품에 반영됐다고 주장하지 않는다.

- 서울 CSV의 80개 격자와 KST `02/05/08/11/14/17/20/23:00` 발표 주기를 유지한다.
- 매시간 `:53` 실행하며 발표 후 40분이 지난 최근 24시간의 주기만 조사한다.
- 최신 수집과 누락 복구는 순서대로 실행하는 별도 GitHub job이다. 각 프로세스는
  발표분 하나만 처리하고 독립적인 20분 예산을 사용한다. 최신 job은 가장 최근 발표분,
  복구 job은 재시도 대기 중이 아닌 가장 오래된 공백을 처리한다. 24시간보다 오래된
  backfill은 수행하지 않는다.
- 주기별 고정 run ID와 R2 checkpoint가 재실행의 재개 지점이다. 실패한 부분 수집은
  정상 완료로 표시하지 않으며 검증된 raw 참조를 다음 실행에서 재사용한다.
- `load_date`는 최초 실제 수집의 KST 날짜다. 자정을 넘어 재시도해도 checkpoint의
  날짜를 유지하며 `collected_at`과 원본 예보 발표 시각을 따로 보존한다.
- 완전한 manifest가 이미 있으면 API 요청이나 완료 시각 덮어쓰기 없이 건너뛴다.
  raw는 조건부 불변 쓰기, checkpoint는 재개 상태, manifest는 완료 증거다.
  완료 검사는 raw의 내용·페이지 완전성·SHA256 metadata까지 다시 대조한다.
  손상된 과거 주기는 격리하고 최신 정상 주기는 계속 수집하되, 작업 결과는
  degraded/실패로 드러낸다. 손상된 원본이나 완료 기록을 자동 덮어쓰지 않는다.

일일 품질 workflow는 기존대로 09:17에 전날을 평가하고 21:43에 미발행 날짜만
재시도한다. 이는 수집 workflow의 프로세스 성공이 아니라 R2 완료 manifest를
읽어 실제 커버리지와 최신성을 평가한다. 장애로 미수집된 주기를 정상으로 바꾸지 않는다.
과거에 발행한 실패 리포트는 불변으로 보존한다. 복구 시점이 하루 중간이면 첫 일일
리포트의 일부 누락은 정상적인 관측 결과이며 다음 완결일의 증거로 회복을 판단한다.

## 호출·시간·쓰기 경계

1000행/page, 격자별 최대 2 pages, 원본 응답 최대 512KiB, 실행별 물리 HTTP 시도
최대 1280회, 프로세스별 내부 실행 예산 20분, job별 제한 25분이다. 최신 job 뒤
복구 job을 직렬 실행하므로 한 workflow는 두 job의 시간을 사용할 수 있다. 실제
source 요청을 병렬화하지 않으며 재시도 대기와 HTTP 요청도 각 예산을 소진한다.
실패 원문 URL·키·provider 응답은 출력하지 않는다.

실제 HTTP 시도 전에 R2의 당일 KST ledger를 조건부 갱신한다. ETag `If-Match` 또는
최초 `If-None-Match`로 실행 간 예산을 보존하고 하루 최대 2400회를 허용한다.
충돌·손상·권한 오류는 fail closed이며 예약 뒤 실패한 요청도 소비한 것으로 센다.
이 한도는 hosted collector 전용이다. 같은 기상청 키의 다른 소비자를 포함한 전역
할당량 또는 외부 계정의 승인 한도를 증명하지 않는다. 로컬 SQLite로 전역 한도를
증명한다고 주장하지 않는다.

완료 주기의 무결성 검증은 metadata-only 검사가 아니다. 최근 8개 주기가 모두
완료됐다면 최대 1280개 raw GET과 해시 HEAD를 수행할 수 있고, 각 객체가 상한
512KiB라면 raw 다운로드만 최대 약 640MiB/실행이다. 실제 페이지와 객체 크기를
측정한다. 본문·해시 검증은 최대 4개의 R2 읽기 worker로 처리하고 집계는 주 스레드에서
수행한다. 검증을 생략하는 receipt나 metadata-only 우회는 도입하지 않는다. API 요청이 0이라는 사실을
R2 읽기량이나 실행 비용이 0이라는 의미로 해석하지 않는다.

R2 쓰기는 hosted 수집기의 raw run과
`ops/control/checkpoints/weather-hosted`, `ops/control/weather-hosted/api-budget`,
`ops/control/weather-hosted/repair-retry`
상태에 제한한다. 삭제·버킷 생성·이력 이관은 하지 않는다. 전용 Object Read/Write
token은 기존 버킷 하나에만 부여한다. Cloudflare token의 버킷 권한은 코드의 prefix
경계보다 넓으므로 해당 token을 다른 작업에 재사용하지 않는다. 품질 리포트의
read-only token은 그대로 분리한다. 기상청 키와 R2 키는 encrypted repository
secrets에만 전달한다.

## 활성화와 되돌리기

검증된 feature → dev → main PR과 CI를 거친 뒤
`WEATHER_COLLECTION_ENABLED=enabled`일 때만 workflow가 가동된다. 수동 실행도
이 플래그와 main/repository 경계를 따른다. 최초 검증은 `only_latest=true`로
80개 격자 한 주기에 제한하고 원본 수·행·완료 manifest·재실행 멱등성을 확인한다.
그 다음 기본 실행으로 최근 공백의 제한 보수를 확인한다.

`only_latest=true` 또는 `source_issue`가 있는 수동 실행은 최신/지정 발표분 job만
실행한다. 기본 수동 실행과 예약 실행은 최신 job 뒤 복구 job을 실행한다. 최신 job이
실패해도 복구는 실행할 수 있지만 취소, 비활성 플래그, 잘못된 저장소·브랜치에서는
실행하지 않는다. workflow 전체의 기존 concurrency를 유지해 source 요청의 실행기
소유권과 일일 API 예산을 공유한다.

이미 부분 진행이 있는 특정 회차를 우선 재개할 때는 수동 실행의 `source_issue`에
발표 시각의 ISO timestamp를 지정한다. 예: `2026-10-14T05:00:00+09:00`.
실제 실행 시각에서 최근 24시간, 발표 후 40분 문턱을 통과한 정식 회차만 허용한다.
`only_latest=true`와 함께 지정하지 않는다. 실제 수집 시각·일일 예산·원본 계약은
현재 clock을 사용하며 과거로 변경하지 않는다. 완료 회차의 반복은 검증 후 API
요청·쓰기 없이 재사용한다. 이 선택자는 upstream의 `NO_DATA`를 정상으로 바꾸지 않는다.

장애 시 `WEATHER_COLLECTION_ENABLED=disabled`로 새 수집을 막는다. 이미 실행 중인
workflow는 별도로 종료하거나 제한된 예산 안에서 배출한다. 삭제 없이 raw·checkpoint·
실패 기록을 보존한다. 이전 정상 raw와 기존 공개 제품은 유지된다. 코드 되돌리기도
보호된 PR 경로를 사용하며 로컬 Docker/Airflow를 자동 재시작하지 않는다.

GitHub cron은 지연되거나 누락될 수 있다. 다음 hourly 실행이 24시간 안의 공백을
재조정하지만 24시간 이상 중단과 정상 수집 완료를 보장하지 않는다. workflow 실패
알림과 일일 리포트의 fail/unmeasured를 확인하고 반복 실패는 원인을 조사한다.

## 2026-10-14 반복 실패 조사와 진단 계약

`bf688cc`에서 10월 13일 KST 20:08 시작 실행은 `run_deadline`, 14일 03:31과
08:07 시작 실행은 `source_page_contract`로 종료됐다. 14일 11:10 실행 로그에는
실제 `ConnectTimeout`이 있었다. 기존 HTTP 재시도는 429/5xx 상태 응답을 처리했지만
연결 시간초과는 첫 시도에서 종료했으므로 hosted 경로에만 네트워크 재시도를 적용한다.
당시 기본 shared 호출 동작은 유지하고 hosted에서 명시적으로 켰다. 각 물리 요청 전에
기존 R2 예산 예약을 수행하며 최대 4회, 대기 30/60/120초, 20분 실행 문턱을 유지한다.
크기·시간 문턱 예외는 연결 장애로 오분류하여 재시도하지 않는다. 이 당시의 hosted
재시도 횟수와 대기는 아래 2026-10-17 정책으로 대체했다.

14일 11:10 KST 읽기 전용 확인에서 13일 17:00 회차는 160페이지와 완료 manifest가
있었다. 14일 02:00은 53페이지, 05:00은 5페이지의 체크포인트를 보존했다.
이 218개 객체의 HEAD metadata는 체크포인트 해시와 일치했고 누락은 없었다.
이 결과는 본문 전체 해시 재계산이나 저장소 전체의 유실 부재를 증명하지 않는다.
미완료 회차를 완료로 표시하거나 해당 raw를 삭제하지 않는다.

두 미완료 지점은 각각 02:00의 `nx=59, ny=125, page=1`, 05:00의
`nx=61, ny=130, page=1`이었다. 동일 지점을 11:16 KST 제한 조회했을 때는
HTTP 200, resultCode 00 및 기존 페이지·격자 계약을 통과했다. 과거 실패 응답이
보존되지 않아 당시 실패한 세부 필드는 확정할 수 없다. API 응답 계약이나
페이지 상한을 완화해 우회하지 않는다. GitHub 실행 환경의 연결 오류와 응답 검증
오류를 구분하며, 로컬 정상 응답을 hosted 복구 성공으로 해석하지 않는다.

실패 summary는 요청 회차·격자·페이지, 고정 검증 규칙, 숫자 페이지 metadata,
두 자리 resultCode, 마지막 검증된 checkpoint 페이지 수와 쓰기 확인 여부를 남긴다.
provider 메시지·본문·URL·버킷명·객체 키·자격 증명은 출력하지 않는다.
`source_page_contract`는 해당 회차의 실패와 checkpoint를 보존하고 다음 선택 회차를
진행한다. 결과는 degraded 및 exit 2로 유지한다. 연결·스토리지·예산 오류는 전체
작업을 멈추며, 중단 전 완료된 회차 수와 물리 시도 수를 실패 summary에 보존한다.

배포 후에는 정확한 main commit의 필수 CI와 별도로 `only_latest=true` 수집 실행,
실패 summary 또는 완료 manifest의 80개 격자·페이지·SHA256, 멱등 재실행을 확인한다.
원본 예보의 freshness와 과거 누락은 일일 품질 리포트에서 따로 평가한다.

`ec73e85`의 run 38502144997에서 14일 08:00, `nx=61, ny=130, page=1`은
`response_business`, resultCode `03`이었다. 11:41 KST 동일 격자의 08:00과
11:00 제한 조회도 `NO_DATA`를 반환했다. 예보 본문이 없어 parser가 pagination
검사 전에 거절했다. 앞선 checkpoint 5페이지는 보존됐다. 이 근거는 과거 모든
`source_page_contract` 실패가 같은 원인이었다고 증명하지 않는다. upstream이
제공하지 않은 격자의 자료를 합성하거나 80개 격자 계약을 줄이지 않는다.

hosted landing은 코드 `03`인 페이지만 해당 격자의 미완료 상태로 보존하고 다음
격자를 진행한다. 정상 응답은 기존 검사·불변 raw 쓰기·checkpoint를 거친다.
어떤 `NO_DATA`라도 남으면 완료 manifest 생성 전에 원래 오류를 다시 발생시키고
모든 미제공 격자·페이지를 실패 summary에 기록한다. 재개 시 검증된 페이지를
재사용하고 빠진 페이지만 요청한다. 공유 Airflow 호출의 기본 중단 동작은 유지하며
네트워크·스토리지·무결성·일반 스키마 오류는 이 정책으로 넘기지 않는다.

## 2026-10-14 예약 전달 복구 시도

16:10 KST 조회에서 수집의 마지막 자연 예약 실행은 11:10 KST의 run
`38499616027`이었다. 현재 main `cd07f8c` 이후 예정된 12:47, 13:47, 14:47,
15:47 실행 기록은 없었다. 품질 workflow는 같은 actor와 현재 main으로 13:58에
자연 실행됐다. 두 YAML과 cron, 기본 브랜치, 활성화 변수, 동시 실행 상태를
검사해 설정 오류는 확인하지 못했다. 이는 수집 코드 전의 예약 전달 문제를
가리키지만, GitHub 내부 등록·대기열의 원인은 공개 API로 확정할 수 없다.

[GitHub schedule 문서](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#actor-for-scheduled-workflows)는
비활성 예약 workflow의 cron을 write 권한 사용자가 변경하면 재활성화되고 그
사용자가 actor가 된다고 설명한다. 현재 수집 workflow는 `active`이므로 이 규칙이
그대로 적용되거나 내부 재등록이 성공한다고 보장하지 않는다. 단일 cron을
`47 * * * *`에서 `53 * * * *`로 변경해 통제된 복구 시도를 수행한다.

빈도는 시간당 한 번이며 별도 수집 예약을 추가하지 않는다. 최신 회차를 요청하는
시점만 6분 늦어진다. 전환 시점에 따라 인접 예정 시각의 간격은 6분 또는 66분이
될 수 있다. main 병합 직전에도 진행 중 실행을 확인하고 기존 동시성 제어를 유지한다.
기존 concurrency, 발표 후 40분, 24시간 창, 요청·시간 예산과 checkpoint 계약은
유지한다. 실행 시각은 실제 clock이며 과거 회차나 결과를 합성하지 않는다.

feature → dev → main PR 및 필수 CI 후 새 main의 `event=schedule` 기록을
확인한다. 생성과 종료 결과, 완료 manifest 또는 미완료 checkpoint·누락 격자를
각각 검증해야 하며 수동 실행을 자연 예약 성공으로 사용하지 않는다. 한 번의
자연 실행도 장기적인 예약 전달이나 원본 자료 복구 전체를 보장하지 않는다.
되돌리기는 보호된 PR로 단일 cron 분을 :47로 복원한다.

## 2026-10-17 실행 예산과 source 복구 분리

현 버전의 완료된 예약 실행 16건 중 13건이 실패했다. 최종 종료 사유는 내부
`run_deadline` 8건, source `03` 3건, HTTP timeout 2건이었다. 일부 실행은 최신
발표분을 정상 완료한 뒤 두 번째 복구에서 중단됐다. 160페이지를 저장하고도 최종
검증 전에 시간이 끝난 checkpoint도 있었다. 일일 리포트 job 성공과 실제 자료의
커버리지·최신성 통과를 구분해야 한다.

최신 수집 job과 복구 job은 각각 발표분 하나와 독립된 시간 예산을 가진다. 완료
manifest와 checkpoint 페이지의 본문·해시 검증은 작은 R2 읽기 worker 풀로 처리한다.
재사용된 페이지 때문에 내용이 같은 checkpoint를 계속 다시 쓰는 비용도 줄인다.
source 요청 자체는 직렬이며 예산·TLS·크기·페이지·80격자 문턱은 유지한다.

HTTP 연결/읽기 오류·429/5xx와 HTTP 200 안의 source `03` 재시도는 hosted 경로의
한 물리 시도 상한을 공유한다. 별도 중첩 재시도로 요청 수를 곱하지 않는다. 마지막
`03`은 성공으로 변환하지 않고 미완료 격자로 보존한다. source의 `Retry-After`가
남은 시간보다 길면 서버 지시를 무시하고 빨리 재호출하지 않고 중단한다. 다른 인증·
스키마·무결성 오류를 일시적 오류로 확대하지 않는다.

중단된 두 페이지 격자의 첫 페이지와 새 두 번째 페이지를 섞지 않는다. 이미 완전하게
검증한 다른 격자는 재사용하고 불완전한 격자만 처음부터 다시 받는다. 제외된 옛 raw는
삭제하지 않으며 새 완료 manifest의 근거로 사용하지 않는다. 페이지별 total count가
달라진 응답은 완전한 격자로 확정하지 않는다.

복구 실패 발표분은 전용 retry 기록에 다음 시도 시각을 남긴다. 3시간 대기 중에는
다른 공백을 처리하므로 한 발표분의 지속적인 `03`이 모든 복구 기회를 독점하지 않는다.
완료된 발표분의 재실행은 source 호출과 상태 쓰기가 없어야 한다. 대기·만료·미완료는
summary와 일일 품질 결과에서 확인하며, 24시간 창 밖의 과거 누락은 자동으로
정상화하지 않는다.

배포 검증은 동일 main SHA의 최신 수집, 160페이지 발표분의 완료 또는 재개,
동일 발표분 재실행의 source 0회·쓰기 0회, 독립된 R2 본문·페이지·해시 확인을
포함한다. 실행 요약의 단계별 시간으로 20분 예산 대비 여유를 확인한다. 품질
workflow의 `refresh=true`로 재평가를 추가하되 기존 일일 실패 리포트는 보존한다.
최신성 회복과 과거 누락 상태를 각각 제시하며 한 번의 성공을 장기 운영 보장으로
해석하지 않는다. GitHub의 예약 전달 지연과 upstream의 실제 자료 미제공은 남은
외부 의존성이다. 실패 알림을 끄거나 부분 자료를 완전한 자료로 표시하지 않는다.
