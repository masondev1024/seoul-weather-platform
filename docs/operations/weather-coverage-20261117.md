## 수집 변경과 되돌리기

최신 발표를 먼저 수집하고, 별도 보충 job에서 아직 24시간 이내인 공백을 오래된 순서로 최대 두 회차까지 처리한다. 하루에 예약 실행이 세 번이면 기존 구성으로는 여섯 회차, 변경 후에는 조건이 좋을 때 아홉 회차까지 처리할 기회가 있다. 하루 발표는 여덟 회다. 실제 처리량은 이미 완료된 회차, 원천 응답, 체크포인트, 시간·호출 예산에 따라 달라진다.

보충 두 건은 순차 실행하고 기존 일일 KMA 호출 상한 2,400회와 완료 기록 검증을 공유한다. 원래의 640개 품질 기준은 유지한다. 업무 영향은 최신 발표 도착 지연과 누락률을 나란히 본다. 보충 시간이 최신 실행을 반복해서 지연시키면 보충 한도를 기존 1회로 되돌린다. 자연 실행 기회 자체가 계속 부족하면 별도 스케줄러 필요성을 다시 판단한다.

## 배포 후 7일 비교

[수정 전 실측 JSON](evidence/weather-coverage-baseline-20261111.json)에 11월 11~17일 결과와 판독 코드·격자 목록의 SHA-256을 고정했다. 읽기 전용 R2 환경 변수는 기존 일일 리포트와 같다. 아래 첫 명령은 기준선을 독립적으로 재산출하고, 둘째 명령은 보관된 기준선으로 비교한다. 실행마다 새 로컬 파일명을 사용한다.

```sh
python -m tools.weather_coverage_comparison --baseline-start 2026-11-11 --output baseline.json
python -m tools.weather_coverage_comparison --baseline-file docs/operations/evidence/weather-coverage-baseline-20261111.json --rollout-at "$ROLLOUT_AT" --output comparison.json
```

`ROLLOUT_AT`에는 구버전의 마지막 진행 중 실행이 끝난 시각과 새 SHA의 자연 예약이 변경된 보충 경로를 실제로 실행한 시각 중 늦은 쪽을 시간대와 함께 넣는다. 해당 SHA와 실행 링크를 함께 기록한다. 배포 다음 날부터 온전한 KST 7일을 사용하며 마지막 날의 다음 날 09:17 이후 두 구간이 모두 측정 가능하다. 배포가 늦어져 바로 직전 주의 수치가 필요하면 전환 전에 09:17 마감이 지난 마지막 발표일부터 역산해 연속 7일의 기준선을 추가로 고정한다. 결과와 함께 배포 SHA, 날짜별 자연 실행 횟수, 수동 수집·중단 여부를 남긴다. 다른 변경이나 예약 횟수 차이가 있으면 코드 변경만의 효과로 해석할 수 없다.

배포 시각을 지정하지 않으면 기준선만 생성한다. 실제 배포 전에는 개선율을 기입하지 않는다. 저장소나 원본 데이터의 과거 삭제·덮어쓰기는 현재 읽을 수 있는 불변 객체만으로 복원할 수 없다.

판단 지표는 동일 4,480개 조합의 커버리지 차이(%p), 전부 최신인 날 수, 미측정 일수다. 보충을 늘린 뒤 최신 수집 마감 지연, API 예산 초과 또는 체크포인트 미완료가 늘어나는지도 Actions 요약에서 확인한다. 운영이 시작되지 않은 기간이나 근거가 부족한 날짜는 0건으로 채우지 않는다. 24시간 수집 창이 지난 발표에 대해서는 분모를 줄이거나 원본을 만들어 채우지 않는다.

### 예약 관측 기록

첫 자연 수집의 실제 보충 실행을 확인한 뒤, 운영 저장소 변수에 `WEATHER_COVERAGE_FIRST_RUN_ID`(해당 Actions run ID), `WEATHER_COVERAGE_ROLLOUT_AT`(위 전환 시각, 시간대 포함)를 순서대로 설정한다. 기존 Weather Daily Quality 자연 예약의 별도 job이 첫날 마감 이후부터 읽기 전용 R2 자격으로 비교한다. 예약이 늦어져도 각 날짜의 기준 시각은 다음 날 09:17 KST로 고정된다.

Actions 실행의 `weather-coverage-<전환 UTC>-<성숙 일수>of7` artifact에는 비교 JSON과 첫 자연 실행 ID, 판독 커밋 및 측정 실행 ID가 들어간다. 같은 날 정상 결과가 있으면 이번 측정은 건너뛴다. 증거 부족은 별도 artifact에 기록하고 해당 job을 실패 처리해 다음 예약에서 재시도한다. 마지막 날 마감 이후 재시도 기간은 7일이고, artifact 보관 기간은 90일이다. 최종 결과를 내려받은 뒤 활성화 변수를 해제할 수 있다.
